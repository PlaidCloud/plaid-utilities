# Changelog

## 1.37.0

- `get_select_query` refuses an aggregate config that projects a bare source column which is neither grouped nor aggregated, instead of emitting invalid SQL (sc-30766). A target column carrying `agg: 'dont_group'` — or no `agg` key at all — was emitted unwrapped in the SELECT list, while `grouping_columns` admits only `agg` `'group'`/`'group_null'`, so the column appeared in neither the GROUP BY nor an aggregate: `SELECT CAST(region AS STRING) AS region, note AS note FROM sch.src GROUP BY sch.src.region`. It is **dtype-agnostic** — a `text` column produces the identical shape a vector column does, so this is not a vector defect — and every warehouse this package targets rejects it: `dialects.REQUIRED_DIALECTS` is exactly StarRocks, Databend, Databricks and Snowflake, and all four enforce GROUP BY. **So no step of this shape runs anywhere today**; this is not a behaviour-preservation question, and the failure it replaces is an engine syntax error naming a character offset rather than the column the user has to fix. Adding the column to the GROUP BY is not an available fix either: the realistic trigger is a `vector` column, and plaid's dtype-role gate refuses grouping a vector outright (`not joinable_as_key-capable`), so refusing is the only option that does not send the user round a loop. The refusal is a `SQLExpressionError`, which plaid's step dispatcher renders verbatim (`execution/error_text.py`), and it names the target column, its source column, its current aggregation, and a remedy chosen from what the dtype can actually do — a `vector` refuses both `joinable_as_key` and `default_agg`, so for it the message says neither "Group By" nor "choose an aggregation", both of which the platform would itself refuse. The check is deliberately narrow, so that nothing valid today is refused. Only the plain `source` path is checked: an `expression` is the user's own SQL and routinely supplies its own aggregate — `agg: 'dont_group'` plus an aggregating expression is the documented way to write one, and the Alteryx Summarize *Concat*, *WeightedAvg*, Cross Tab, Calgary and data-profile conversions are built that way across ~24 `alteryx_mapper` sites and 9 in `data_explorer/sql_generator` — while deciding whether an arbitrary expression aggregates would mean guessing at function names, including UDAFs we cannot know. The GROUP BY is read for the columns it actually references, keyed on the `Table` object rather than its name, so grouping on an expression does not wave the check through and two sources sharing a table name (the same name in two schemas, which `frame_join_multi` accepts) are not confused; a source column the GROUP BY already references is fine, since `SELECT region, region AS region_copy ... GROUP BY region` is legal. Constants are exempt and their `agg` is ignored entirely when deciding whether the query aggregates — `constant_from_clause` hard-passes `None`, so a constant's `agg` never reaches the SQL, and `frame_join_multi` derives its `aggregate` flag over every target column including constants, so a constant at `agg: 'sum'` would otherwise have armed the refusal against innocent passthrough columns. `serial`/`bigserial` and the magic dtypes are not exempted by anything: they fall out of the check for carrying no `source`, which is the only way they render as `row_number()` or a magic literal at all. A `count` query projects only `count(*)`, and a config that turns aggregation on but names no grouping column and no real aggregate is not an aggregate query at all — no GROUP BY is emitted, so the projection is plain valid SQL, which is how `frame_join_anti`'s existence subquery is built. New `is_passthrough_agg` and `column_contributes_an_aggregate` are the one definition of "this agg leaves the value alone", exported so callers stop restating it: `frame_join_multi` spells it `tc.get('agg') and tc.get('agg') != 'dont_group'`, which misreads `dont_group_null` (`get_agg_fn` strips the `_null` suffix and returns `ident`, and it is not a grouping token either). Known gap, disclosed rather than papered over: a projected column the GROUP BY references only *inside* a larger expression (`GROUP BY lower(region)` while projecting bare `region`) still passes, because proving functional dependence through an arbitrary expression is not something this check can do. Asserted against the **rendered StarRocks SQL string**, both for the refusals and for every shape that must keep rendering byte-for-byte as it did ([@inviscid](https://github.com/inviscid)).

- Value-parity fixes for the StarRocks `@compiles` variants that predate sc-30376 (sc-30414). Each one compiled cleanly and answered a different value than Databend, so nothing failed: `integerize_truncate` squashed through a bare `DECIMAL`, which is `DECIMAL(10, 0)` on StarRocks and therefore **rounds** before `truncate()` runs (`'2.7'` was `3` on StarRocks and `2` on Databend) — it now pins `DECIMAL(38, 10)`, the same fix the Snowflake variant already carried; `regexp_substr` returned `''` rather than `NULL` when nothing matched, so `IS NULL` tests and `coalesce()` fallbacks over it were wrong on every non-matching row; `regexp_instr` was a plain rename to `regexp()`, which answers `1`/`0` rather than the 1-based match offset; `import_cast` dropped Databend's whitespace squash (so `'1 234'` imported as `NULL`), routed trailing negatives through a format mask StarRocks ignores (so `'123-'` imported as `NULL` instead of `-123`), and cast `'t'`/`'f'` straight to `BOOLEAN`, which is `NULL` on StarRocks.
- `to_char(<number>, '<0/9 mask>')` and `to_number(...)` now refuse on StarRocks instead of answering differently than Databend (sc-30414). `to_char` returns a string, so silently dropping a Postgres numeric mask changed the column's contents; `to_number` renders `to_int64` (an integer) on Databend and had no StarRocks rendering that returns the same type. Both refusals are derivable — `TO_CHAR_STARROCKS_UNSUPPORTED_NUMERIC_MASK` and `_STARROCKS_UNSUPPORTED` — so the lakehouse pre-flight scan blocks the project by name rather than the migration rewriting values.
- SQLAlchemy is capped below 2.1. `snowflake-sqlalchemy` subclasses `sqlalchemy.orm.context.ORMSelectCompileState`, which 2.1 renamed, so loading the Snowflake dialect raises `AttributeError` — and 2.1 also renamed `_DropView` and switched `postgresql://` to psycopg3. Unpinned, this repo's test suite went red on master the day 2.1.1 published.

## 1.36.0

- New `vector_distance(metric, a, b)` SQLAlchemy construct (`metric` leads, positional; `cosine` or `l2` only — inner product is excluded). On StarRocks it compiles to `(1 - cosine_similarity(a, b))` for `cosine` and `sqrt(l2_distance(a, b))` for `l2`; every other dialect raises `CompileError`, since the vector dtype is StarRocks-only. Cosine distance is **not** bounded below by zero: an exact match returns about `-1.19e-7` (StarRocks' `cosine_similarity(v, v)` is `1.0000001` in float32), so a `distance >= 0` or `BETWEEN 0 AND 2` filter silently drops exact matches — the top hit (sc-30364).

- Route every dtype site in this package through plaid-rpc's fail-closed admission boundary (`admit_dtype` / `require_dtype_capability`), so an undeclared dtype is refused by name instead of becoming a silent default. `frame_manager.sql_from_dtype` raised a bare `KeyError`, which every `except KeyError` upstream swallows; `dtype_from_sql` held an 11-entry map and answered `None` for everything else — including `uuid`, `json`, `serial`, `bigserial`, `tinyint`, `double` and `largebinary`, all of which analyze declares — and that `None` was what made `set_column_types` report `dtype conversion of <col> to None FAILED`, naming the wrong thing. It now reads the registry's `pandas` declaration, so those six convert (`serial` and `bigserial` as `Int64`, `tinyint` as `Int8`, `double` as `float64`, `json` and `largebinary` as `object`) and `uuid`, `bitmap`, `geometry` and `geography`, which have no pandas representation, refuse by name. `set_column_types`' numeric branch gains the nullable integer spellings (`Int8`/`Int16`/`Int64`) the registry actually uses — load-bearing, not tidying: without them every integer column would fall through the branch chain unconverted. `converter_from_sql`, which `load_typed_psv` consumes alongside `dtype_from_sql`, held its own 11-entry map against that function's 20, so a typed psv naming `serial`, `double` or `json` refused there while resolving here; it is now derived from `dtype_from_sql`'s answer, one converter per pandas dtype the registry can name, so the two cannot disagree. Three wrappers that swallowed the refusal are narrowed so it reaches the caller: `set_column_types`' bare `except:`, which caught the exception the function itself raised and re-raised a different one; `load_typed_psv`'s two `except ValueError` blocks, which guarded a header column carrying no type and so read a refused dtype as "this is an untyped csv"; and `frame_join_multi_validator._dtype_ok`'s `except Exception`, which made an `ImportError` indistinguishable from an unresolvable dtype. `_dtype_ok` also replaces a hand-kept enum of 20 dtype tokens over a fallback that accepted anything `sqlalchemy_from_dtype` resolved — so a dtype became a legal join key and aggregation target the moment it gained a SQLAlchemy type — with a check **per role**: admission only for a declared source column, since most merely pass through; `joinable_as_key` for both operands of a column-to-column join condition (reasons `left_expr_dtype_not_joinable`, `right_expr_dtype_not_joinable`, `between_bound_dtype_not_joinable`); and `default_agg` for an aggregated target column (reason `target_column_dtype_not_aggregatable`). A `BETWEEN` whose bounds are both literals is a filter, not a join key, and is left alone. Counting is exempt throughout — `COUNT` and `COUNT(DISTINCT)` read no value semantics, so they stay valid for a dtype that refuses every other aggregation. The reason-token vocabulary the module docstring has always pointed at now exists as `_REASONS`, with a test that keeps it exhaustive in both directions. `sql_expression.get_from_clause` gains the emitter's only per-dtype aggregation decision: `get_agg_fn` dispatches through `getattr(sqlalchemy.func, ...)` and asks nothing about the column, so a dtype the registry declares unaggregatable otherwise reached the warehouse as `SUM(<array>)` and failed there, in another repo, naming neither the column nor the dtype. The axis is `default_agg` (`None` meaning the dtype refuses aggregation), not `aggregatable`, which means only "is this a numeric you can SUM": gating `MIN`/`MAX` on that would refuse `MIN(<text>)` and `MAX(<timestamp>)`, which are valid SQL and which `frame_lookup` emits for every non-key column of its dedupe subquery. Two pre-existing defects in the functions touched are fixed with them: `converter_from_sql` read `pd.datetime`, removed in pandas 2.0, so every call raised `AttributeError` and `load_typed_psv` answered nothing at all; `set_column_types`' timedelta tuple concatenated `'timedelta64[Y]'` and `'interval'` for want of a comma (dead, since `dtype_from_sql` renders `interval` as `timedelta64[s]` before the lookup, but the tuple claimed a token it did not hold); and a typed psv returned the **text** of a date, time, timestamp or interval rather than the value — the first three because declaring a column `object` defeats `parse_dates` (pandas honours the dtype and skips parsing), the fourth because `read_csv` refuses a timedelta `dtype=` and the converters that would have parsed it reach only the `ValueError` retry path. Both now come back as real `datetime64`/`timedelta64` values. **Release ordering**: this needs plaid-rpc ≥ the release carrying sc-30345. This package's own floor on `plaidcloud-rpc` is raised to `>=1.16.0` in `requirements.txt` and `pyproject.toml`: the floor was `>=1.11.0`, which an unbounded resolve satisfies with a version that has no `admit_dtype`, so a constrained install or a lockfile could pair this code with an rpc that `ImportError`s at import. The rpc release must ship first (sc-30354). `plaid` and `workflow-runner` both **exact**-pin `plaidcloud-utilities` and are on different versions (1.33.0 and 1.34.0), so this package's release needs two independent pin-bump PRs, not one (sc-30348) ([@inviscid](https://github.com/inviscid)).

- `apply_rules` (SQL) gives one row per source row when rules run in more than one iteration, as the pandas engine does. It evaluated each iteration as its own pass over the source and `UNION ALL`ed the passes, so every source row came out once per iteration: once with that iteration's matched rule and values, or with nothing where it matched none. Iterations are overrides, a later iteration replacing values an earlier one set, so a rule-based tagging step on SQL wrote a copy of every row for each iteration, and an allocation's mapping carried every row once per iteration too. Every iteration now picks its matched rule in one pass. A target column takes its value from the latest iteration whose matched rule sets it; a rule holding a blank value (`''`, `'None'`, `'nan'`) or null sets nothing, and a text column that every matched rule leaves blank reads `''` rather than whichever marker a rule held. A rule holding null leaves the column NULL, where pandas has `''`, as a single iteration has always done. `rule_number` and `rule_id` join the matched iterations' values with `', '` (`'1, 2'`), so with more than one iteration `rule_number` is text, as pandas writes it. A single iteration generates the same SQL as before and keeps `rule_number` an integer. An iteration with no valid rules is skipped instead of rendering `CASE END`, which no warehouse accepts. `include_once=False` is unchanged. **This needs the matching workflow-runner change to ship with it**: the runner counts a rule's matched rows by joining the mapping table's `rule_id` to the rules on equality, and a row matched in two iterations now carries a joined id (`'R2, R3'`) that matches neither, so every rule that only matches after the first iteration would have a count of 0 written back onto its assignment dimension. Allocated values and tags are unaffected (sc-29921) ([@rad-pat](https://github.com/rad-pat)).
- The remote dimension client's `rename_dimension`, `shift_node_right`, `shift_node_left`, `shift_node_up` and `shift_node_down` now send what the server accepts; each had raised on every call, the rename with `old`/`new` for a server that takes `duid`/`name` (the client now takes those too), the shifts with a single `child` for a server that takes a `children` list and answers with a list, so the client wraps and unwraps. `Dimension.reload` is deleted, since no server has the method, and a call that falls through `__getattr__` now returns the server's answer instead of dropping it ([@rad-pat](https://github.com/rad-pat)).
- Render Alteryx **TitleCase** on Databend, Databricks and DuckDB, which previously raised `CompileError` — StarRocks was the only target that could run it, so any converted workflow carrying a Data Cleanse title-case step or a `TitleCase()` formula failed on every other warehouse. StarRocks' native `initcap` is the contract the rest now match: a word is a run of alphanumerics and every other character delimits, so `o'brien-smith` titles to `O'Brien-Smith`. Databend and DuckDB have no such builtin, and Databricks' `initcap` splits on whitespace alone — it is rendered by hand rather than called, because a silently different answer is worse than a missing function. Those three mark each word start with a U+0001 sentinel, split there, case each chunk and rejoin: one array element per word, and the column expression is evaluated once. The word class is `[\p{L}\p{N}]`, not ASCII `[[:alnum:]]`, because StarRocks classifies with ICU and would otherwise disagree on `café ñino`. Snowflake keeps its native `initcap` but is now passed the delimiter set explicitly — the default omits the apostrophe, backtick and equals sign, so it alone returned `O'brien`; non-ASCII punctuation still fails to delimit there and cannot be enumerated. The default still raises for any other dialect, so a fifth target cannot inherit an unchecked rendering. Verified by executing the Databend render against a live 1.2.790 server and the DuckDB render in the test suite, both against StarRocks' algorithm ([@rad-pat](https://github.com/rad-pat)).

Every Dependabot PR in the run history failed this way; PRs from people were unaffected, which is why it read as noise rather than as a job nobody could get green. Nothing is lost with it: the step ran `fail_below_threshold: false`, so it never failed a PR on coverage either way, and `Check Patch Coverage` already writes a coverage table to the job summary. It also removes the last Node 20 action in this repo — `5monkeys/cobertura-action` is unmaintained (last commit March 2024, manifest still `using: 'node20'`), so there was no newer version to move to; GitHub was already forcing it onto Node 24 and warning about it on every run ([@simozzy](https://github.com/simozzy)).

- New `sql_expression.resolve_target_dtypes(target_columns, source_column_configs, tables=None, ...)`, the list form of the null-dtype resolution sc-23460 added, so a caller can resolve once and hand the answer to every consumer (sc-23870). `_target_dtype` runs inside `get_from_clause`, which fixes the emitted SQL and nothing else — but a step also *declares* its target table from the same config, and that path reads the raw dtype, so an untyped output column still died at `RegexMapKeyError: 'none'` **before** the query it had just been fixed for was compiled. That is why sc-23460's fix did not make an already-saved step run. **Resolving freezes the answer**: any truthy dtype is returned unchanged from then on, so a caller holding the table objects must pass them as `tables` rather than expect the query build to correct it. Without them a column name several sources carry under *different* dtypes is ambiguous and resolves to `text` — a semantic narrowing, since a numeric column cast as text loses arithmetic and ordering, and chosen over guessing a side (`CAST(<text column> AS NUMERIC)` is rejectable where the reverse is not) and over leaving the null in place (which puts the declaration and the CAST back into disagreement). Returns shallow copies, so a config that is round-tripped or persisted keeps its dtype: typing a column permanently stays the user's decision, via the step form. `get_table_rep` additionally stops raising on a **null** dtype, defaulting to `text` — a backstop for a caller that has not pre-resolved, inert once one has. An *absent* `dtype` key still raises as it always has: that is a malformed config, and most of this function's callers are representing a *source* table, where quietly declaring text would mistype a column the query reads. **Library half only** — the runner half lands separately, and until both deploy the repair is still to set the column's **Type** in the step form and re-save ([@simozzy](https://github.com/simozzy)).
- Stop every timestamp parsed on StarRocks from landing NULL. `to_timestamp`, `to_date` and `to_char` translated their format string with `postgres_to_python_date_format` and handed the result to `str_to_date`, `str2date` and `date_format` — MySQL-family functions, which read MySQL specifiers. The two vocabularies collide on the most common token in a datetime format: on StarRocks `%i` is the minute and `%M` is the **full month name**, the opposite of Python. `YYYY-MM-DD"T"HH24:MI:SS` therefore reached StarRocks as `%Y-%m-%dT%H:%M:%S`, which asks it to read `22` as a month name; `str_to_date` returns NULL for a format it cannot match, so the column arrived empty and the step reported success. Measured on StarRocks 4.1.3: `str_to_date('2026-08-03T14:22:31', '%Y-%m-%dT%H:%M:%S')` → `NULL`, `str_to_date('2026-08-03T14:22:31', '%Y-%m-%dT%H:%i:%S')` → `2026-08-03T14:22:31`. The same misreading on the output side made `to_char(ts, 'HH24:MI:SS')` render `14:August:31`. Formats now go through a new `postgres_to_starrocks_date_format`, built from the StarRocks `date_format` specifier reference the way `postgres_to_snowflake_date_format` was built from Snowflake's, and both inbound dialects (Postgres tokens and Python strftime) normalize through it. Postgres double-quoted literals become bare text, since StarRocks has no quoting inside a format string and a literal `"T"` would otherwise stop `2026-08-03T14:22:31` matching. Three tokens have no StarRocks specifier and now raise `CompileError` rather than rendering as bare characters: `TZ` and `tz` (StarRocks has no timezone specifier at all) and `D` (Postgres numbers the week 1-7 from Sunday, StarRocks' `%w` numbers it 0-6). This reaches every timestamp column of a CSV/text-staged import on a StarRocks workspace, and every `to_timestamp`/`to_date`/`to_char` in a transform expression, converted Alteryx workflow or view; Parquet imports were never affected, because they compile `import_col` to a bare typed staging column under `typed_staging_compilation()` and never build a format string. Databend, Snowflake, Postgres and Greenplum SQL is byte-for-byte unchanged. Tested by parsing a real value with the emitted format rather than by matching the compiled SQL against a pattern — a pattern test passed the broken code for as long as it existed ([@inviscid](https://github.com/inviscid)).
- New `plaidcloud.utilities.dialects`: the set of SQL dialect drivers an image must carry to build a `query.Connection`, declared beside the code that enforces it, plus `assert_dialects_available(image, requirements_file)` and a `python -m plaidcloud.utilities.dialects <image> <requirements-file>` build step for consuming images. Since sc-23700 a missing driver raises at query time instead of compiling Postgres SQL against Databend or StarRocks; carrying the required set in the same wheel as that raise makes the pin bump self-verifying — an image short a driver fails its own build, in whatever order the pin bump and the driver addition happened — and replaces the per-image copy of the list in `workflow-runner`. Greenplum is deliberately not in the set ([@inviscid](https://github.com/inviscid)).
- Stop a target column with a missing or **null** `dtype` crashing `get_from_clause` with `RegexMapKeyError: 'none'` (sc-23460). `sqlalchemy_from_dtype(None)` stringifies its argument before the regex lookup, so `None` becomes the key `'none'` and raises rather than returning a type — which took out both the save (a 500 from the step form: "Update Failed – Internal Server Error") and the step run, for any join/lookup output column the client wrote without one. The dtype now resolves through `_target_dtype`: the configured value if it's set, else the dtype of the matching source column, else `text`. Falling back to the source column rather than straight to `text` is what keeps a summed numeric column numeric instead of silently stringifying it. Where several sources carry the same column name, the dtype is read off the one the query actually selects from — resolved by the same `get_column_table` precedence (`source_alias`, a `tableN.col` reference, the legacy `source_table`) that decides which column is emitted, so the cast matches the column being cast. Only a name that stays ambiguous after that resolution falls through to `text` rather than picking a side, because guessing wrong yields a cast the warehouse can reject (`CAST(<text column> AS NUMERIC)`) where casting a numeric column to text cannot; `text` is otherwise the last resort, and matches what the step forms' own column default has always been (and what `plaid`'s expression validator already back-filled for a dtype key that was *absent* — this closes the same gap for a key that is present and null). The `largebinary` no-cast check resolves the same way, so a null-dtype binary column still isn't cast. A dtype that is set but genuinely unrecognised still raises, as before. This supersedes the "behavior for a missing/unresolvable `dtype` is unchanged" note on the expression-coercion entries below ([@simozzy](https://github.com/simozzy)).
- `analyze_table.compiled` now raises when given no dialect instead of silently compiling Greenplum SQL. Greenplum is no longer a lakehouse engine, so the fallback named an engine that cannot exist and turned a lost dialect into SQL for a warehouse nobody runs rather than an error. Every `compiled()` call site in `plaid` already passes a real dialect, so nothing there changes. The deprecated `analyze_table.send_query` has no dialect to pass and now raises for a SQLAlchemy query — build queries through `plaidcloud.utilities.query.Connection`, which knows the project's datastore. Removed the deprecated `AnalyzeTable.head`, its only in-repo caller: it passed `send_query` three positional arguments against a four-parameter signature and read `project_id` as a bound method, so it could never have returned rows. This is one site of a wider Greenplum-default sweep, not the whole of it (sc-23700) ([@inviscid](https://github.com/inviscid)).

- Security: sandbox the transform-expression engine so an authored expression can no longer execute arbitrary Python. `eval_expression`/`eval_rule` now run under a pinned restricted `__builtins__` and a strict allowlist guard: only a curated set of AST node types is permitted, no dunder/underscore attribute may be traversed (bar a single-underscore SQL-function name off `func`), `str.format`/`format_map` are blocked, and an attribute chain rooted at the raw `sqlalchemy` module is confined to type/expression helpers — which closes `sqlalchemy.text` raw-SQL and the module-re-export escapes (e.g. `sqlalchemy.log.logging.os.system(...)`) that a denylist could not. Legitimate SQL expressions (including `func._if`, `func.format`, and `sqlalchemy.cast`) are unaffected ([@simozzy](https://github.com/simozzy)).
- Allow `sqlalchemy.select` in the expression sandbox so scalar-subquery expressions (e.g. the Table Explorer facet's distinct-count) evaluate again, while blocking the raw-SQL splice methods it exposes (`prefix_with`/`suffix_with`/`with_hint`/`with_statement_hint`) — reachable on a `select(...)` result or a subquery's `.element` back-reference — so `select` cannot reintroduce a `text()`-style raw-SQL vector ([@simozzy](https://github.com/simozzy)).
- Add the `currency` dtype (`DECIMAL(18, 4)`, via plaidcloud-rpc >= 1.9.0 `PlaidCurrency`): accepted by the frame_join_multi validator, `import_cast` branches for HANA/Databend/StarRocks, `currency` in the expression cast vocabulary, and float64/Avro-`double` read mappings in frame_manager ([@inviscid](https://github.com/inviscid)).
- File imports load empty cells in `currency` columns as 0.0, matching numeric's behavior ([@inviscid](https://github.com/inviscid)).
- Compile keyword-based `date_add` expressions to StarRocks-compatible SQL so StarRocks dashboard filters run without parser errors.
- Add StarRocks specializations for the SQL functions the Alteryx expression converter emits, so converted expressions run on StarRocks as well as Databend. Each keeps the existing Databend/default SQL unchanged and adds only a StarRocks form: regular-expression match/extract, `to_string`/`try_to_float64` casts, `modulo`, `ord`, `today`, the date-part extractors (`to_year`/`to_month`/…), the `add_*` date-add family, and unit-parameterized `date_diff` ([@inviscid](https://github.com/inviscid)).
- Close the remaining non-spatial StarRocks gaps: add StarRocks forms for `to_char` (dates via `date_format`, other values cast to `CHAR`), `to_number` (`CAST(... AS DECIMAL(38, 10))`, which also fixes the `import_cast` trailing-negatives path that previously emitted a nonexistent `to_number`), `transaction_timestamp` (`now()`), `string_to_array` (`split`), `ascii`/only-ASCII (3-arg `regexp_replace`), and `normalize_whitespace` (3-arg `regexp_replace` with RE2 `\x{…}` code-point escapes). The Databend/default SQL is byte-for-byte unchanged; every StarRocks form was verified executing live ([@inviscid](https://github.com/inviscid)).
- Add a durable dialect-neutral spatial function layer (`geom_from_wkt`, `geom_point`, `geom_as_wkt`, `geom_contains`, `geom_x`, `geom_y`, `geom_within`, `geom_area`, `geom_length`, `geom_intersects`, `geom_createline`, `geom_centroid`, `geom_distance`): each renders the current Databend `ST_*` spelling on Databend/default and the verified StarRocks equivalent on StarRocks (`geom_within` swaps args into `st_contains`). Ops with no transparent StarRocks equivalent (`geom_area`, `geom_length`, `geom_intersects`, `geom_createline`, `geom_centroid`, and `geom_distance` — planar vs. spherical `st_distance_sphere`) raise a clear `CompileError` on StarRocks so callers degrade to the shapely executor rather than emit wrong SQL ([@inviscid](https://github.com/inviscid)).
