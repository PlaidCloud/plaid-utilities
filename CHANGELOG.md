# Changelog

## Unreleased

- `analyze_table.compiled` now raises when given no dialect instead of silently compiling Greenplum SQL. Greenplum is no longer a lakehouse engine, so the fallback named an engine that cannot exist and turned a lost dialect into SQL for a warehouse nobody runs rather than an error. Every `compiled()` call site in `plaid` already passes a real dialect, so nothing there changes. The deprecated `analyze_table.send_query` has no dialect to pass and now raises for a SQLAlchemy query — build queries through `plaidcloud.utilities.query.Connection`, which knows the project's datastore. Removed the deprecated `AnalyzeTable.head`, its only in-repo caller: it passed `send_query` three positional arguments against a four-parameter signature and read `project_id` as a bound method, so it could never have returned rows. This is one site of a wider Greenplum-default sweep, not the whole of it (sc-23700) ([@inviscid](https://github.com/inviscid)).

- Reject a rule whose condition compiles to no SQL in `apply_rules` instead of emitting a statement that is either unparseable or silently wrong. The per-iteration `valid_rules` filter checks the condition *text* — non-null and non-empty — but the predicate actually placed in the query is `eval_rule(...)` of that text, and nothing checked what that produced. A condition of `and_()` is non-empty text that compiles to an empty `BooleanClauseList`, and the two code paths then fail in opposite ways: with `include_once` the `case()` emits a branch with no condition at all (`WHEN  THEN 'C0005'`) and the warehouse rejects the whole statement, which on Databend surfaces as `QueryFailed: [1005]` pointing at a character offset in a 40 000-character query and naming neither the step nor the rule; without `include_once`, SQLAlchemy drops a `WHERE` built from an empty predicate, so the rule matches every source row, the run completes, and the allocation is quietly wrong. Both now raise `SQLExpressionError` naming the offending `rule_id` and its condition text. The check is `str(predicate)` on the unbound expression — empty for a zero-clause `and_()`, non-empty for any real predicate, and needing neither a dialect nor a bind context — plus an explicit `is None` arm, because a condition of `null` evaluates to Python `None` whose `str()` is the non-empty `'None'` and would otherwise slip through to a `WHEN NULL THEN` that never matches. A genuine catch-all (`and_(true)`) is unaffected, and so is a rule using a construct that only compiles on one warehouse — `str()` renders under the *default* dialect, where a dialect-specific compiler raises, so a failed render is read as "not renderable here", never as "empty", and the rule passes through to the dialect that can run it. That applies whatever the compiler raises: `titlecase` raises `CompileError` but `slice_string` raises `NotImplementedError`, so the render probe treats *any* exception as "not empty" rather than guessing at a type; a genuinely broken expression still fails at execution, against the dialect that has to run it and with a message about that dialect. The generator that was producing `and_()` — a rule-hierarchy node with no source criteria — is fixed in workflow-runner, so this is defense in depth for that case; it still stands on its own for any other condition that compiles away, and it turns the existing failure into a one-line diagnosis for a tenant running an older workflow-runner against this release (sc-23440) ([@inviscid](https://github.com/inviscid)).
- Gate PR CI on **patch coverage** (coverage of the lines a PR changes) at 80%, via `diff-cover` pinned to 10.4.1, and stop implying a global gate that never existed. The `5monkeys/cobertura-action` step carried `minimum_coverage: 75` against a repo sitting at 57% overall, but that action's `fail_below_threshold` defaults to `false`, so it reports the GitHub `neutral` conclusion — which does not fail a pull request. Every PR merged green with the threshold unmet and the file table marked with crosses; verified on #356, whose `coverage` check run reports `conclusion: neutral` beside a `57%` total and a `Minimum allowed coverage is 75%` footer. A global threshold is also the wrong instrument mid-refactor: 57% is historical debt, not any one PR's quality. The new `Check Patch Coverage` step measures only the changed lines, so untouched legacy files cannot block a PR while changed lines in traced modules must be 80% covered. Note the job is not currently **enforced**: `master`'s branch protection lists no required status checks (`required_status_checks.contexts` and `.checks` are both empty, and the repo has no rulesets), so this gate fails the job but does not block a merge until `Lint PlaidCloud Utilities w ReviewDog` is added to the required set — owed follow-up, and an owner decision. `actions/checkout` gained `fetch-depth: 0` — at the default depth-1 there is no merge-base with the base branch to diff against, and `diff-cover` would have reported "No lines with coverage information in this diff" and exited 0, a false pass. The step deliberately does **not** carry the `!cancelled()` condition its neighbouring report steps use: a failed `pytest` leaves `coverage.xml` stale or absent, so a coverage number computed then would be meaningless and would bury the real test failure. The cobertura step stays, unchanged in purpose — its per-file table is a useful annotation — but is now explicitly `fail_below_threshold: false` with `minimum_coverage` dropped from 75 to the repo's actual 57, so a cross means "below the repo average" rather than advertising a gate. A docs-only PR that changes no measured source line still passes ([@inviscid](https://github.com/inviscid)).
- Build the `values` dict in `get_update_query` with a plain loop instead of a dict comprehension over a nested list comprehension that concatenated tuples (`(tc['source'],) + get_update_value(...)`). No behaviour change — it is the same construction its sibling `get_update_rewrite_query` already used, so the two functions now read identically ([@inviscid](https://github.com/inviscid)).
- Reject an update config with nothing to set in `get_update_query` instead of emitting invalid SQL (sc-23414). `get_update_value` excludes a non-text column carrying no `constant`, no `expression` and no `nullify`; when that excluded every mapped column the values dict was empty and `update(table).values({})` compiled to `UPDATE … SET  WHERE …` — a `SET` with no assignments, which the warehouse rejects with a syntax error naming neither the step nor the column. A user reaches this by dragging a numeric column into a Table Update step's Update Columns mapper and leaving Constant, Expression and Set Null all blank; the step saves cleanly and fails at run. It now raises `SQLExpressionError` naming the update columns, mirroring the guard `get_update_rewrite_query` already carries for the same config. A text column is unaffected — `get_update_value` returns `''` for a text column with no value, so it stays in the `SET` list — and so is `get_delete_query`, which maps no columns and cannot produce an empty `SET`. The live Table Update executor moved to `get_update_rewrite_query` in workflow-runner #1148, so this reaches tenants still pinned to the earlier executor, for which `get_update_query` remains the Databend, Postgres and Greenplum path ([@inviscid](https://github.com/inviscid)).
- Add `get_update_rewrite_query`, the projection form of `get_update_query`, so an update step can write its result to a target table on engines that have no row-level `UPDATE`. StarRocks rejects `UPDATE` on Iceberg tables outright (`table … does not support update`), which is why the Table Update step was pulled from the client's New Step menu; the same outcome is reachable as a plain `SELECT` provided the filter is translated rather than reused. The wheres pick which rows get *updated*, not which rows come back, so they compile to a `CASE` condition on each mapped column (`CASE WHEN <where> THEN <value> ELSE <column> END`) and every source row is projected — mapped columns conditionally, unmapped columns as passthroughs. `CASE` falls through to `ELSE` for both FALSE and NULL, which is precisely what `UPDATE … WHERE` does; the obvious alternative of two filtered branches unioned together silently drops every row whose condition evaluates to NULL, since such a row satisfies neither `<where>` nor `NOT <where>`. Value semantics are not reimplemented — the same `get_update_value` drives both functions, so `nullify`, `constant`, `expression` and the text-dtype-blank quirk behave identically whichever query shape is used, and a non-`ClauseElement` value is wrapped in a typed literal so an unconditional `nullify` still carries its column's type. One deliberate difference from a plain projection: `update().values()` rejects a key that is not a column of the table, and losing that check would turn a stale mapping into a step that reports success having updated nothing, so an update column absent from the source raises `SQLExpressionError` naming it, and a config with nothing to update at all — every update column missing a constant, an expression and Set Null — is rejected rather than compiling to an exact copy of the source (the equivalent `UPDATE ... SET` with no assignments was invalid SQL, so that config always failed loudly). `get_update_query` is untouched and remains the path for Databend, Postgres and Greenplum ([@inviscid](https://github.com/inviscid)).
- Preserve binary source columns during external-database imports instead of casting them through a database-specific binary type; SQL Server rowversion columns now load as binary values.

- **Multi-Table Join** source and target tables accept dynamic references, like every other step: a table name, a project path (`/03 Results/FACT_GL`), or either carrying `{variable}` tokens, alongside the canonical `analyzetable_<uuid>` id. The `frame_join_multi` validator previously required a bare identifier, so a step configured with the table picker's **Dynamic** mode could not be saved at all — the workflow-runner executor has always resolved these through the same `get_frame()` every other step uses (variable substitution, path or name lookup, and create-if-missing for the target); only the save-time gate disagreed. The gate was justified as keeping dots, quotes, and whitespace out of the emitted SQL, but the reference never reaches SQL — `get_frame()` resolves it to a canonical id first and the query is built from that, and the lookups on the way are parameterised RPC calls. What is still rejected is a reference that cannot resolve under any variable values: a non-string, empty or whitespace-only, longer than 512 characters, containing control characters, or carrying unbalanced braces — that last one raises inside `apply_variables`' `Formatter().parse()`, so catching it at save turns a mid-run crash into a message on the step form. Accepting `{variable}` grants no new reach: the tokens resolve against the caller's own project/workflow variables, exactly as `frame_extract` has always done, and `apply_variables` runs strict, so a field name that isn't a plain defined variable (`{x.__class__}`) fails its undefined-key check before `str.format` is reached ([@inviscid](https://github.com/inviscid)).

- Run the Alteryx Summarize **Mode** aggregate on StarRocks instead of failing closed. `mode(col)` previously raised `CompileError` on StarRocks ("no StarRocks equivalent; run this workflow on a Databend workspace"), which is what the live corpus workflow `02 Learn_one_tool_at_a_time/Summarize.yxmd` hit. StarRocks 4.1.3 genuinely has no `mode()` aggregate, and the exact rewrite — count per (group, value) in a CTE, then take the highest count — is a two-stage query that cannot be built from a compile hook filling a single aggregate slot (the GROUP BY keys are assembled separately, in `sql_expression.get_select_query`). `mode` now compiles to the single-expression `approx_top_k` form instead: `array_filter(array_map(sr_mode_e -> sr_mode_e.item, approx_top_k(col, 2, 100000)), sr_mode_i -> sr_mode_i IS NOT NULL)[1]`, verified executing live on StarRocks 4.1.3. **Two divergences to be aware of.** (1) The result is *exact* for any group with fewer than 100000 distinct values — StarRocks: "Expressions that have fewer than `counter_num` distinct items will yield exact item counts", and 100000 is the documented maximum `counter_num` — and only above that does it become a Space-Saving estimate (count error up to `2.0 * numRows / counter_num`), where Databend's `mode()` is always exact. (2) Ties are broken by `approx_top_k`'s internal counter order: arbitrary but deterministic for a given input, whereas Alteryx returns the first-encountered value and Databend leaves it unspecified — no two of the three targets agree on ties. NULL handling *does* match: `approx_top_k` counts NULL as its own item and will return it as the winner, so the rewrite asks for the top 2 (NULL is at most one item, so the top 2 always contain the most frequent non-null value if the group has one) and filters nulls out; an all-null group yields NULL, as on Databend. The `mode() WITHIN GROUP (ORDER BY col)` ordered-set spelling has nothing to count and still raises a clear `CompileError` on StarRocks; it is unchanged on every other dialect. Databend/default SQL is byte-for-byte unchanged (`mode(c)`) ([@inviscid](https://github.com/inviscid)).

- Make the StarRocks **Median** aggregate exact and consistent with Databend. `median(col)` compiled to `percentile_approx(col, 0.5)` — a t-digest estimate, so a StarRocks workspace could return a different median than a Databend one for identical data. It now compiles to `percentile_cont(col, 0.5)`, which is exact and linearly interpolates the two middle values on an even count: the same answer both Alteryx's Summarize→Median and Databend's `median()` give. `percentile_disc(col, 0.5)` was rejected because it returns an actual member of the input instead (3, not 2.5, for `[1, 2, 3, 10]`), which matches neither. `percentile_cont` also accepts DATE and DATETIME, not just numerics as `percentile_approx` does, so median over a date column now works too. Being exact, it holds the group's values rather than a sketch, so a median over a very large group costs more memory than the old estimate did. Databend/default `median(c)` is unchanged ([@inviscid](https://github.com/inviscid)).

- Fix a v1.20.0 regression that broke eight previously-passing Alteryx-converted workflows (including `Union.yxmd` and `Poly-Split Build.yxmd`) with `Target column '<name>': expression 'None' compiled to None/NULL`. v1.20.0 made `expression_from_clause` **raise** when a calculated target column's expression evaluated to Python `None`; it now **coerces** to an explicit SQL NULL instead. A converted Alteryx `Null()`, an empty formula, and an unmapped-but-harmless column all legitimately mean SQL NULL, and the executor cannot distinguish those from a genuinely unmappable formula — so raising turned working conversions into hard failures. `expression_from_clause` now substitutes `sqlalchemy.null()`, which `process_fn` casts to the target column's dtype exactly as before v1.20.0 (`CAST(NULL AS NUMERIC)`, etc.), and emits a `WARNING` naming the target column and the source expression. The reasons the v1.20.0 guard existed are preserved: the bare `None` still never reaches SQLAlchemy (no opaque `AttributeError` in the `INSERT … from_select` column scan), and the NULL is no longer silent because it is logged. The fail-closed signal for formulas that genuinely could not be mapped already exists upstream at **convert** time in `plaid` (`apply_formulas_to_target_columns` emits `sqlalchemy.null()` plus a `runtime_unmapped_note` and low confidence), so the executor does not need to be — and cannot correctly be — the enforcement point. Behavior for a missing/unresolvable `dtype` is unchanged: it still raises upstream in `get_from_clause` at `sqlalchemy_from_dtype` ([@inviscid](https://github.com/inviscid)).
- Drop three unused runtime dependencies: `argparse` (in the Python standard library since 2.7 — pinning it installed a redundant PyPI backport), `setuptools` (nothing imports it or `pkg_resources` at runtime), and `avro` (no module imports it; `frame_manager.avro_from_sql` only maps SQL types to Avro type *names*). Consumers of this package no longer install them ([@inviscid](https://github.com/inviscid)).
- Move `ipython` from a base dependency to an optional `jupyter` extra (sc-23365). `data_helpers.jupyter_table` is the only IPython consumer and already imported it lazily, so IPython (and its `jedi` dependency, ~30 MB) is no longer pulled into every image that installs `plaidcloud-utilities`. Notebook users install it with `pip install plaidcloud-utilities[jupyter]`; calling `jupyter_table` without IPython present now raises a clear `ImportError` naming the extra instead of a bare `ModuleNotFoundError`. No other module imports IPython, so all non-notebook imports and the rest of `data_helpers` are unaffected ([@inviscid](https://github.com/inviscid)).
- *(Shipped in v1.20.0; superseded by the coercion entry at the top of this section — the raise described below no longer happens.)* Fail closed when a calculated target-column expression compiles to Python `None` instead of a SQL clause, rather than letting the `None` flow into the query and surface as an opaque failure. An Alteryx-converted column whose formula is unmapped/empty — or a bare `None`/`null`/`NULL`/`Null` (all of which `get_safe_dict` maps to Python `None`) — used to fail in a way whose exact shape depended on dtype and SQLAlchemy version: a silent, wrong-data `CAST(NULL)` when a cast_type was present, or an `AttributeError` deep in SQLAlchemy's `INSERT … from_select` column scan (`'NoneType' object has no attribute 'is_sequence'`, or `… has no attribute 'label'` for `serial`/`bigserial` columns, whose cast_type is falsy) — in every case naming neither the step nor the column. `expression_from_clause` now raises a clear `SQLExpressionError` naming the target column and the source expression the moment the expression evaluates to `None`. A genuine NULL column is unaffected: it must be written as a real clause (`cast(null, <type>)` or `sqlalchemy.null()`), both of which evaluate to a `ColumnElement`, not bare `None`; and the legitimate `count_null` path (which sets the source column to `None` and wraps it in `func.count`) goes through `source_from_clause`, not this guard. Note: a target column with a missing/`None` `dtype` is a separate degeneracy that still raises upstream in `get_from_clause` at `sqlalchemy_from_dtype` (`RegexMapKeyError: 'none'`) before this guard is reached ([@inviscid](https://github.com/inviscid)).

- *(Superseded in part by the Mode entry at the top of this section: `mode` no longer raises on StarRocks, it compiles to `approx_top_k`. The spatial entries below still stand.)* Make converted Alteryx spatial/statistical functions with no StarRocks equivalent fail with a clear, immediate error instead of a cryptic warehouse "No matching function" failure (sc-23271). The bounding-rectangle edges (`st_xmin`/`st_xmax`/`st_ymin`/`st_ymax`, from Alteryx SpatialInfo Rect), the CreatePolygon fallback (`st_makepolygon`), and the statistical **Mode** aggregate (`mode`) now raise a clear `CompileError` on StarRocks naming the function and pointing to a Databend workspace, matching the existing `geom_area`/`geom_length` fail-closed behavior. The Databend/default SQL is byte-for-byte unchanged, and the `mode() WITHIN GROUP` ordered-set form is left intact (a StarRocks compiler is attached to SQLAlchemy's built-in `mode`, not an override) ([@inviscid](https://github.com/inviscid)).

- Stop `frame_join_multi` rejecting valid converted-Alteryx joins (sc-23307). The step validator required each source/target column `dtype` to be one of a small closed set of lowercase tokens and each column `id`/target name to be a bare SQL identifier — but the converter (and MCP/hand-authored steps) legitimately emit PlaidCloud/pandas dtype aliases (`String`, `Int32`, `Float64`, `datetime64`, …) and real column names with spaces and punctuation (`Position Title`, `Years (starting at 1st grade)`). Both are what the executor already handles — it builds each column's type via `sqlalchemy_from_dtype` and quotes the name through SQLAlchemy — so the validator now accepts any dtype that mapper resolves and any column name that is non-empty, ≤255 chars, and free of the quote/control characters that could break out of a quoted identifier. Genuinely unresolvable dtypes and quote-injection names are still rejected (sc-23307) ([@inviscid](https://github.com/inviscid)).

- Fix `get_select_query`/`get_from_clause` crashing with `AttributeError: 'str' object has no attribute 'get'` when a column mapping's `sort` is the string enum `'asc'`/`'desc'`/`'none'` instead of the dict form (`{'ascending': bool, 'order': int}`) the UI persists. REST/MCP step saves have written the string form into tenants (notably `sort: "none"` on every programmatically created import step), so the sort handling now normalizes both shapes at the choke point: `'asc'` sorts ascending, `'desc'` descending, and `'none'`/null/absent means no sort. Dict and null configs compile byte-identically to before (sc-23317) ([@inviscid](https://github.com/inviscid)).

- Render string-typed `CAST`s as `STRING` on StarRocks instead of `CHAR`. StarRocks inherits MySQL's CAST rules (string types → `CHAR`), but `CHAR` maxes at 255, so a `String`/`Text` cast emitted `CHAR(4000)` — tolerated in a bare `SELECT` but rejected by the strict `INSERT … UNION` type check against a `STRING`/varchar column ("input cols type not equal with output cols type"), which broke converted Alteryx Union workflows. Non-string casts are unchanged (sc-23267) ([@inviscid](https://github.com/inviscid)).

- **Breaking:** remove the dead file-import CSV converters from `frame_manager` (sc-23281): `excel_to_csv`, `fixedwidth_to_csv`, `parquet_to_csv`, `yxdb_to_csv`, `avro_to_csv`, plus the yxdb-only helpers `_geojson_to_wkt`, `_yxdb_fixed_decimal_extractor` and `_convert_yxdb_value`. These were public library functions; anyone importing them from a notebook or UDF must vendor a copy or use the plaid-side replacements — the streaming Parquet converters in `plaid/app/analyze/utility/parquet_conversion.py` (Excel/fixed-width/Parquet/YXDB), or `plaid/app/analyze/utility/import_tools.avro_to_csv` for Avro. The import worker no longer imports `frame_manager` at all, which is what removes pandas from its cold start. `json_to_csv`/`get_json_columns` stay — the JSON import step's column-guess dialog still uses them ([@inviscid](https://github.com/inviscid)).

- Add a typed-staging compile switch for file imports (sc-23281): `sqlalchemy_functions.typed_staging` (a `ContextVar`, default off) with the `typed_staging_compilation()` context manager. While set, `import_col` compiles to the bare staging column — the Parquet converter has already parsed, typed and coerced every value (blank→`0.0` for numeric/currency, blank→`NULL` for temporal/integer/boolean, dates parsed, trailing negatives folded) — instead of the text-parsing `regexp_replace`/`import_cast` CASE machinery, which breaks against a typed column (`to_timestamp(<timestamp>, fmt)`). With the flag unset, compilation is byte-identical to before (snapshot-tested across greenplum/databend/starrocks/snowflake for all import dtypes), so the CSV path is unaffected. Because the workflow-runner ships a pickled expression tree and the `@compiles` handler runs in the import worker at execution time, old and new runners need no change ([@inviscid](https://github.com/inviscid)).

- Run Alteryx-converter Median, pick-any, string concatenation, and array-to-text/tail expressions on StarRocks workspaces; TitleCase runs on StarRocks and fails with a clear message on Databend, which has no title-case function (`titlecase`->`initcap`, `median`->`percentile_approx`, `any`->`any_value`, `string_agg`->`group_concat ... SEPARATOR`, `array_to_string`->`array_join`, `array_tail`->`array_slice`) ([@inviscid](https://github.com/inviscid)).

- Fix a step configured to aggregate with **Rollup**, **Grouping Sets** or **Cube** failing outright at the database when none of its output columns is set to Group. With no column carrying agg `group`/`group_null`, `grouping_columns` comes out empty and the query was built as `GROUP BY ROLLUP()` / `GROUPING SETS()` / `CUBE()` — all three are hard SQL parse errors (Postgres: `syntax error at or near ")"`; the empty grouping set is spelled `GROUP BY ()`). Plain Group was never affected, because `group_by()` with no columns is a no-op that emits no `GROUP BY` at all. This is a live production bug, not a latent trap: 22 workflow-runner call sites already forward the step's `aggregation_type` on the currently deployed release — the Join (inner/outer), Union, Union All, Upsert, Lookup, Loader, Allocation, Postman, remote-import, rule-tagging, forecast and condition-check paths, plus the Excel/Avro/Parquet/XML/Templated/Sage exports — and every one of them takes its output columns straight from user configuration, so turning on Summarize, choosing Rollup and leaving every column as a real aggregate (sum, count, …) breaks the step today. The three special forms are now guarded on having something to group on and fall through to plain grouping otherwise ([@inviscid](https://github.com/inviscid)).
- Fix `get_select_query` crashing with `TypeError: unsupported operand type(s) for -: 'NoneType' and 'int'` when a config carries a row-limit key that is present but null. `fill_in` fell back to its documented default only when the key was *absent* — `dict.get(key, default)` returns the stored `None` when the key is present — so `{'use_target_slicer': True, 'limit_target_end': None}` reached `limit_target_end - limit_target_start`. It is reachable from the Table Explorer: clearing or typing non-numeric text into the **Max Rows** box while the Max Rows checkbox is on sends `limit_rows` as JSON `null` (the client does `parseInt(...)`, and `NaN` serialises to `null`), which the server copies straight into `limit_target_end`. The grid preview showed a misleading "Unable to open preview…" alert, and **Download → Limited Row Count** and **Save as View** returned a 500. All nine `fill_in`-guarded params (`aggregate`, `having`, `use_target_slicer`, `limit_target_start`, `limit_target_end`, `distinct`, `count`, `disable_variables`, `aggregation_type`) now treat a present-but-null config value as not supplied, matching how the function already treats an explicit `None` argument. Only the two limit params change behaviour: six of the remaining seven are consumed solely in truthiness tests, where `None` and the `False`/`None` default are interchangeable, and `aggregation_type` is unaffected because its signature default is `'group'` rather than `None`, so its config lookup is reached only when a caller passes the argument as `None` explicitly. A null limit now yields the same `LIMIT 0 OFFSET 0` as omitting the key entirely; callers are expected not to send a slicer with no row count (PlaidCloud's table explorer now clamps that case before it reaches this function) ([@inviscid](https://github.com/inviscid)).
- Fix expression validation rejecting `is`, `is not` and `not`, which broke saved calculated-field, filter and rule expressions that had run for years (e.g. a lookup step failing with "Is is not permitted in an expression."). The three operators were omitted from the expression allowlist in error; they add no escape surface and are now accepted again. One family is deliberately still rejected: `not (...)` wrapped around a column comparison (`==`, `!=`, `is`, `is not`, `in`, `not in`) does not build a SQL NOT — it collapses to a constant and silently drops the comparison from the query — so it now fails with a message naming what does work (`!=`, `is_(None)`, `notin_([...])` for a single comparison; `not_(and_(...))`/`not_(or_(...))` when the comparisons are joined by `and`/`or`). A `not (...)` around a comparison of pure constants (no column involved, e.g. `not ('ABC' == 'CORP')`) is correct and is left alone. Note that on a column `x is None` is a Python identity test that is always false — use `x.is_(None)` for a real null test (sc-23186) ([@simozzy](https://github.com/simozzy)).
- Fix expression validation rejecting columns whose name begins with an underscore, which broke steps that reference them (e.g. "Access to attribute '_MajorAccountFlag' is not permitted."). Such a column is reachable as `table._MyColumn` again, while a name that merely looks like one but resolves to SQLAlchemy internals stays blocked (sc-23186) ([@simozzy](https://github.com/simozzy)).
- `PlaidConnection` now forwards `verify_ssl`, so a UDF or notebook can turn TLS certificate verification on or off for a single connection — `PlaidConnection(verify_ssl=True)` — instead of only through the `__PLAID_VERIFY_SSL__` environment variable. Unlike `project_id`/`workspace_uuid`, it is forwarded on every path, because plaidcloud-rpc applies it after choosing a configuration source and so it overrides whichever source supplied the rest. Requires plaidcloud-rpc >= 1.12.0, the first release where `verify_ssl` actually reaches the transport (sc-23168) ([@inviscid](https://github.com/inviscid)).
- `PlaidConnection` now forwards connection configuration to `Connect` ([sc-21805](https://app.shortcut.com/plaidcloud/story/21805)): `rpc_uri`, `auth_token`, `token_provider`, `workspace_uuid` and `project_id` reach the RPC layer instead of being silently discarded, so `PlaidConnection(rpc_uri=..., auth_token=...)` configures a connection with no environment variables and no `plaid.conf`. Previously `__init__` accepted `*args`/`**kwargs` and then called `Connect.__init__(self)` with none of them, which made plaidcloud-rpc's new direct-argument API unreachable from the connection class the generated UDF boilerplate actually uses. Forwarding is by explicit name, not `**kwargs` — `xl_path` is consumed by `PlaidConnection` itself and `Connect` would reject it. `project_id` is passed through only alongside `rpc_uri`, since without it the environment or `plaid.conf` supplies the project. Requires plaidcloud-rpc >= 1.11.0 ([@inviscid](https://github.com/inviscid)).

- The `uuid`/`Uuid`/`UUID` cast type in transform expressions (calc fields, filters, rules) now uses the platform's canonical `GUIDHyphens` type instead of the Postgres-only `UUID`, so an inline uuid cast compiles valid SQL on every lakehouse engine (StarRocks previously dropped the cast entirely) and produces the same 36-character hyphenated form that uuid-typed columns store. Only the inline-expression cast path changes — column dtype configuration (`sqlalchemy_from_dtype('uuid')`) already used `GUIDHyphens` and was never affected (sc-23158) ([@inviscid](https://github.com/inviscid)).

- Security: sandbox the transform-expression engine so an authored expression can no longer execute arbitrary Python. `eval_expression`/`eval_rule` now run under a pinned restricted `__builtins__` and a strict allowlist guard: only a curated set of AST node types is permitted, no dunder/underscore attribute may be traversed (bar a single-underscore SQL-function name off `func`), `str.format`/`format_map` are blocked, and an attribute chain rooted at the raw `sqlalchemy` module is confined to type/expression helpers — which closes `sqlalchemy.text` raw-SQL and the module-re-export escapes (e.g. `sqlalchemy.log.logging.os.system(...)`) that a denylist could not. Legitimate SQL expressions (including `func._if`, `func.format`, and `sqlalchemy.cast`) are unaffected ([@simozzy](https://github.com/simozzy)).
- Allow `sqlalchemy.select` in the expression sandbox so scalar-subquery expressions (e.g. the Table Explorer facet's distinct-count) evaluate again, while blocking the raw-SQL splice methods it exposes (`prefix_with`/`suffix_with`/`with_hint`/`with_statement_hint`) — reachable on a `select(...)` result or a subquery's `.element` back-reference — so `select` cannot reintroduce a `text()`-style raw-SQL vector ([@simozzy](https://github.com/simozzy)).
- Add the `currency` dtype (`DECIMAL(18, 4)`, via plaidcloud-rpc >= 1.9.0 `PlaidCurrency`): accepted by the frame_join_multi validator, `import_cast` branches for HANA/Databend/StarRocks, `currency` in the expression cast vocabulary, and float64/Avro-`double` read mappings in frame_manager ([@inviscid](https://github.com/inviscid)).
- File imports load empty cells in `currency` columns as 0.0, matching numeric's behavior ([@inviscid](https://github.com/inviscid)).
- Compile keyword-based `date_add` expressions to StarRocks-compatible SQL so StarRocks dashboard filters run without parser errors.
- Add StarRocks specializations for the SQL functions the Alteryx expression converter emits, so converted expressions run on StarRocks as well as Databend. Each keeps the existing Databend/default SQL unchanged and adds only a StarRocks form: regular-expression match/extract, `to_string`/`try_to_float64` casts, `modulo`, `ord`, `today`, the date-part extractors (`to_year`/`to_month`/…), the `add_*` date-add family, and unit-parameterized `date_diff` ([@inviscid](https://github.com/inviscid)).
- Close the remaining non-spatial StarRocks gaps: add StarRocks forms for `to_char` (dates via `date_format`, other values cast to `CHAR`), `to_number` (`CAST(... AS DECIMAL(38, 10))`, which also fixes the `import_cast` trailing-negatives path that previously emitted a nonexistent `to_number`), `transaction_timestamp` (`now()`), `string_to_array` (`split`), `ascii`/only-ASCII (3-arg `regexp_replace`), and `normalize_whitespace` (3-arg `regexp_replace` with RE2 `\x{…}` code-point escapes). The Databend/default SQL is byte-for-byte unchanged; every StarRocks form was verified executing live ([@inviscid](https://github.com/inviscid)).
- Add a durable dialect-neutral spatial function layer (`geom_from_wkt`, `geom_point`, `geom_as_wkt`, `geom_contains`, `geom_x`, `geom_y`, `geom_within`, `geom_area`, `geom_length`, `geom_intersects`, `geom_createline`, `geom_centroid`, `geom_distance`): each renders the current Databend `ST_*` spelling on Databend/default and the verified StarRocks equivalent on StarRocks (`geom_within` swaps args into `st_contains`). Ops with no transparent StarRocks equivalent (`geom_area`, `geom_length`, `geom_intersects`, `geom_createline`, `geom_centroid`, and `geom_distance` — planar vs. spherical `st_distance_sphere`) raise a clear `CompileError` on StarRocks so callers degrade to the shapely executor rather than emit wrong SQL ([@inviscid](https://github.com/inviscid)).
